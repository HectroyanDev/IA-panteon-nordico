# Re-revisión

Un comentario es de Tyr si su cuerpo contiene `Generated by Tyr-skill`. Solo cuentan los comentarios raíz inline con un hallazgo (los que empiezan por 🔴, 🟡 o 🔵), sin resolver.

## Clasificación

Para cada uno, compara la zona anclada en el commit que se revisó con la del head actual:

| Estado | Cuándo | Acción |
| --- | --- | --- |
| `fixed` | La causa descrita ya no se da en el head (el código cambió y el problema desaparece) | Responder "✅ Resuelto" y resolver el hilo |
| `pending` | El código sigue igual o el cambio no elimina la causa | Responder "⏳ Sigue pendiente" si no hay ya una respuesta pendiente de Tyr para el mismo SHA; cuenta para el veredicto con su gravedad |
| `outdated` | El archivo o la zona ya no existen y el problema no reaparece en otro sitio | Resolver el hilo sin responder |

- Si el autor ha respondido justificando por qué no lo cambia, no decidas tú: márcalo `pending` y añádelo a la vista previa para que el humano diga si se acepta (entonces se resuelve).
- No crees un hallazgo nuevo que repita uno `pending`.

## El fix también se revisa

Las líneas que cambiaron para arreglar un hallazgo previo forman parte del diff de la PR y pasan por las tres lentes como el resto. Cada lente recibe la lista de hallazgos previos con su zona para fijarse en si el arreglo:

- introduce otro bug (rompe un caso que antes funcionaba, cambia un contrato público);
- tapa el síntoma sin quitar la causa (p. ej. escapa la salida pero sigue concatenando SQL);
- deja código muerto o duplicado.

Lo que encuentren va como hallazgo nuevo inline.
